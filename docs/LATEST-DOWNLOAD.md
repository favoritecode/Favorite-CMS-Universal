# Automatic latest stable CMS download

Permanent URL: https://favoritecode.github.io/Favorite-CMS-Universal/download/

## Setup and recovery

The complete, self-contained implementation is `.github/workflows/latest-download-pages.yml`.
In Settings → Pages, select **GitHub Actions** as the source. This was previously disabled;
there was no existing Pages site or publishing branch to replace. No website hosting change,
PAT, extra repository secret, release upload, or ZIP rename is required.

For initial deployment or recovery, open Actions → Latest stable download (Pages) → Run workflow
and use `main`. Wait for the `github-pages` environment deployment to finish successfully.
Publish future stable releases normally, with one uploaded asset named exactly
`Favorite-CMS-Universal-v<VERSION>.zip`, matching the release tag `v<VERSION>`.
Keep the release marked as GitHub's latest stable release. Drafts and prereleases are not selected.

## Implementation

The workflow uses the authenticated official `/repos/{owner}/{repo}/releases/latest` API,
validates published/stable flags and selects the exact tag-matching uploaded ZIP asset. It ignores
source archives, checksum files, test candidates and unrelated extension assets. It validates the
GitHub owner/repository/tag download URL rather than accepting an arbitrary external redirect.

The Python `render()` function generates `_site/download/index.html`, which keeps the main page
open and starts a hidden download frame. The frame loads `start.html`, generated by `render_start()`,
with immediate `window.location.replace()` and zero-delay meta refresh. The fallback download link
also targets the frame, so it does not navigate the main page to GitHub.

The responsive download card adapts to the device light/dark preference. A Return to website
button links to https://favoriteweb.net/. A five-second countdown returns there automatically;
Stay here or Download again cancels that countdown. The timer measures elapsed time, not download
completion: browsers do not expose cross-origin download completion to this page. Only this small static site and non-secret asset metadata are deployed. The browser
receives no API token and performs no API call. No release ZIP is copied to Pages.

Release publication, editing, deletion and stable/prerelease transitions trigger regeneration;
manual dispatch and workflow changes also trigger it. An hourly reconciliation catches missed events,
including releases published with `GITHUB_TOKEN` (those do not trigger another workflow).
GitHub scheduling may be delayed, and an inactive public repository's scheduled workflows may be
disabled by GitHub after 60 days. Release events/manual dispatch remain available; re-enable Actions
if GitHub disables them. Release assets should be attached before publishing a release.

Deployments share a serialized concurrency group and do not cancel an in-progress deployment.
Every run fetches current API state twice, never the event's old tag; out-of-order queued runs
therefore resolve current release state. Changes made during a deployment are applied by the next
queued release run or reconciliation. GitHub Pages is static: propagation is asynchronous, not an
atomic redirect update at the instant a release is published.

If no stable release exists, the generated page states that downloads are unavailable, removing
the stale destination. A network/API failure or missing/ambiguous ZIP fails the workflow and leaves
the previous successful deployment intact. Inspect the failed run and retry after correcting the
release asset. The fallback link helps when a browser blocks automatic downloads; browser download
settings, GitHub availability and download permission prompts cannot be overridden by this system.

## Permissions and preservation

Only contents:read, pages:write and id-token:write are used with built-in authentication.
The workflow never checks out or writes CMS files, mutates releases, changes tags or uploads release
assets. Existing workflow files, release packaging, runtime allowlist, signed core, software version,
updater and licensing remain untouched. Future Pages content must be integrated into the same Pages
artifact rather than deployed by a competing workflow that would overwrite this site.

## Tests

Eight built-in tests run before every deployment: current/future stable versions (2.0.0, 2.0.1,
2.0.2, 3.0.0); draft/prerelease/unpublished rejection; source/other asset exclusion;
missing/duplicate/incomplete/hostile asset rejection; immediate redirect plus both fallbacks;
no-stable-release behavior; preservation of the main page URL during download; and return/pause controls. Future-version tests use fixtures, not extra GitHub Releases.

To verify production, inspect the workflow summary and `/download/release.json`, then open the
permanent URL in a browser. Hash the downloaded ZIP and compare with the original release's SHA-256.
Successful CI alone does not prove that a browser actually downloaded the correct asset.
