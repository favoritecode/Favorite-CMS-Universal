# বর্তমান নিয়ম — নতুন installation outage-এ চলবে; registered site-এ শেষ action

এই নির্দেশিকা আগের first-registration block/strict-outage/24-hour grace সম্পর্কিত নির্দেশনার বদলে প্রযোজ্য। Version CMS 1.2.1 ও Server 1.0.1 অপরিবর্তিত; Server correction build 2026112606।

## সাইট কীভাবে চলবে
- সাধারণত installer নিজেই official favoriteweb.net server-এ independent UUID + canonical URL দিয়ে register করবে। প্রথমবার Server/network সাময়িক বন্ধ থাকলে site ও content management চালু থাকবে, registration pending হবে। Normal requests-এ automatic retry প্রথমে ২ মিনিট, পরে ৫/১৫ মিনিট interval-এ হয়। Server ফিরলে পরের সফল retry-তে ownership verification, registration ও signed Owner policy sync হবে; পুনরায় install বা manual key লাগবে না। Pending অবস্থায়ও UUID স্থায়ী থাকে।
- Registration ও publisher-authorized signed state পাওয়া গেলে Active site স্বাভাবিক চলবে। Owner Warning/Suspend/Ban/Reactivate দিলে signed revision অনুযায়ী sync হবে। স্বাভাবিক PHP requests-এ প্রায় ৩০ সেকেন্ড পরপর status যাচাই হয়; traffic না থাকলে PHP নিজে background-এ চলে না।
- Central server/network বন্ধ হলে আগে পাওয়া সর্বশেষ বৈধ signed state অপরিবর্তিত থাকে: Active চলবে, Suspended/Banned বন্ধ ও সংশ্লিষ্ট message দেখাবে। Outage-এ সেই state সময় পার হওয়ার কারণে Active থেকে বন্ধ হয় না; নতুন installation-এর সাময়িক network/5xx/rate-limit ব্যর্থতায় pending access আছে; verification/authentication/security failure-এ নেই। আগে registered site-এ cache/secret নষ্ট হলে pending access দিয়ে আগের action override হয় না। Server ফিরলে পরের successful check-এ নতুন action আসে।
- Cache JSON-এ শুধু active লেখা বা অন্য public key বসানো অনুমতি নয়। Authority certificate, signature, installation/URL binding ও policy revision যাচাই হয়। Publisher delegation certificate বর্তমান সময়ে valid হতে হবে নতুন response নেওয়ার সময়; আগেই গৃহীত signed state তার গ্রহণযোগ্য historical certificate দিয়ে outage-এ যাচাই হয়।
- Protected executable core/vendor/view files-এর signed inventory পরীক্ষা হয়। Theme/plugin/content/settings-এর অনুমোদিত customization ঐ inventory-তে নেই। Update UI unsigned বা mandatory-connection enforcement ছাড়া পুরোনো core build প্রত্যাখ্যান করে।

## আপনার একবারের Owner authority setup — customer-এর কাজ নয়
1. পুরো files/database/private-vault backup নিন। Owner Server correction আগে বসান। আগের reviewed 1.0.1 updater একই version নেয় না: তার জন্য আগের নিরাপদ one-time folder cutover/recovery নির্দেশনা প্রযোজ্য। আগের registration-fix updater higher build 2026112606 নিতে পারে। `.env`, `storage`, vault, keys বা orders মুছবেন না।
2. Central Control → Connection security খুলুন। Owner password confirmation আগের মতোই থাকবে। Public signing request download/save করুন। এতে secret নেই।
3. আপনার আগে দেওয়া encrypted signing backup এবং আলাদা recovery key দিয়ে offline computer-এ নতুন Owner Signing Tools ZIP-এর `sign-authority.php` চালান:
   `php sign-authority.php REQUEST_JSON ENCRYPTED_KEY RECOVERY_KEY OUTPUT_JSON`
   এখানে placeholder-এর বদলে local file path দিন। আমাকে বা অন্য AI-কে ওই local path দিলেও এটি করা যায়; secret chat-এ paste করবেন না।
4. পাওয়া signed public certificate Connection security-তে paste করে Owner password দিয়ে save করুন। Publisher private key hosting-এ upload করতে হবে না। Certificate সাধারণত দুই বছর পর renewal লাগবে; একই offline key দিয়ে নতুন public request sign করা যায়।
5. তারপর CMS mandatory-connection ZIP admin Updates দিয়ে দিন ও customers-কে বিতরণ করুন। Certificate না থাকলে তা authority verification failure; নতুন CMS চালুর আগে certificate বসান। শুধু temporary network outage-এ pending access চলে, authority/authentication failure-এ নয়। নতুন customer-কে manual central URL/license key দিতে হবে না।

আগের Signing Backup ZIP ও recovery key অপরিবর্তিতভাবে কাজে লাগবে। এই release-এর জন্য নতুন Tools ZIP-এর signer ব্যবহার করুন; পুরোনো signer-এর protected path allowlist ছোট ছিল।

## Deleted/replaced site-এর তালিকা পরিষ্কার
- Instant permanent delete নেই। Signed uninstall/retirement এবং Owner-এর existing manual actions বহাল আছে।
- Monitoring-এ পরপর ৩টি replacement/identity mismatch indication, অন্তত ১২ ঘণ্টা ব্যবধানের evidence এবং অন্তত ২৪ ঘণ্টা heartbeat না থাকলে মূল তালিকা থেকে reversible archive হয়। Owner action, UUID, purchase ও audit history মুছে যায় না।
- শুধু timeout/DNS failure হলে তা deletion-এর প্রমাণ নয়। দীর্ঘ ৩০ দিনের unreachable অবস্থা হলে stale entry archive করা যায়; এটি confirmed deletion হিসেবে দেখানো হয় না। Browser/hosting challenge-ও deletion নয়। Authenticated heartbeat ফিরলে archive নিজে থেকে উঠে যায়।
- Automatic monitoring-এর জন্য Owner hosting-এ একবার cron দিন, যেমন প্রতি ১০ মিনিটে PHP দিয়ে `DOMAIN_ROOT/favorite-server-license/scripts/monitor-sites.php` চালান। `DOMAIN_ROOT` আসল absolute hosting path হবে। প্রতি run-এ সর্বোচ্চ ৩টি due site, প্রতিটি site-এর normal interval ৬ ঘণ্টা। বড় fleet হলে frequency/batch scheduling পর্যালোচনা করতে হবে। Central Control → CMS sites & access → Automatic monitoring থেকে manual run ও last-run দেখা যায়। Cron ছাড়া unattended checks চলছে বলে দাবি করা হচ্ছে না।

## বাস্তব সীমা
Public browser access আর server-to-server ownership proof এক নয়। masti.page.gd-এর browser challenge থাকলে ownership verification এখনও আটকে যাবে এবং সেটি outage allowance পাবে না; challenge bypass বা ভুয়া approve করা হয়নি।

নিজের hosting-এর সব PHP/file/network নিয়ন্ত্রণকারী ব্যক্তিকে software alone দিয়ে ১০০% tamper-proof করা যায় না। এই build official runtime, signed updates ও normal operation enforce করে; PHP checks পুরো সরিয়ে ফেলা, modified emulator বা পুরোনো code হাতে বসানো অসম্ভব হয়ে গেছে—এমন দাবি নেই। আগে cache/CDN-এ রাখা static page/image PHP gate না চালিয়েও serve হতে পারে; action rollout-এ full-page cache purging/bypass দরকার।

প্রথমবার offline installation চলতে দিলে কেউ ইচ্ছাকৃতভাবে central network block করেছে কি সত্যিকারের outage—client একা নিশ্চিতভাবে আলাদা করতে পারে না। তাই এই নিয়ম এবং প্রতিটি লুকানো installation শতভাগ আটকানোর দাবি একসঙ্গে দেওয়া যায় না।

Owner-এর server offline থাকলে last state রাখা ও একই সঙ্গে নতুন remote action তখনই পৌঁছানো—দুটো একসঙ্গে সম্ভব নয়। নতুন action successful reconnection-এর পর কার্যকর হয়।

## নতুন Local installation ও Account directory
- localhost, *.localhost, *.local, *.test, private LAN IPv4 এবং IPv6 loopback/ULA URL-এ থাকা installation এখন outbound HTTPS দিয়ে official Server-এ register হয়। দুইটি computer/root-এ একই localhost URL হলেও আলাদা UUID + private installation key থাকে। Local নাম দিয়ে public domain ownership claim করা যায় না; central কখনো localhost/private URL fetch করে না। Dashboard-এ Local · outbound identity এবং প্রকৃত local URL দেখাবে। এটি public-domain verification বা hardware attestation নয়।
- Internet/central connection না থাকলে প্রথম local install pending অবস্থায় চলে। Internet ফিরলে পরের request/retry-এ register হয়। Registered local site-এ Owner Suspend/Ban/Reactivate signed policy অনুযায়ী কার্যকর হয়; outage-এ শেষ state থাকে। Local site সরিয়ে ফেলার অবস্থা বাইরে থেকে নিশ্চিত করা যায় না; তাই inbound monitoring দিয়ে local record auto-delete/archive করা হয় না। Owner manual retirement আছে।
- একই root/machine-এ local URL বা port বদলালে key ও UUID অক্ষত রেখে local binding update হয়।
- Local site পরে public HTTPS URL-এ গেলে, সংযুক্ত identity দিয়ে automatic ownership-verified transfer হয়। ID এবং license identity বজায় থাকে। অন্য root/machine-এ কপি করলে নতুন local identity হয়; copied runtime key থেকে public ownership অনুমোদন করা হয় না।

## Safe recovery — disconnected বা modified site
- Updater request-এ সর্বোচ্চ ৩০০ সেকেন্ডের bounded PHP execution budget চাওয়া হয়; অন্য request-এর global limit বদলায় না। Timeout/fatal interruption ধরতে পারলে FAILED/RECOVERY_REQUIRED status লেখা, maintenance রাখা ও নিজের update lock ছাড়ার ব্যবস্থা আছে। Host-এর hard kill/process limit এর বাইরে এই নিশ্চয়তা নেই। Database migration মাঝপথে থামলে trusted database backup restore আগে; successful authenticated restore-এর পর official file repair আবার করা যায়।
- জরুরি entry: /admin/connection-status অথবা /admin/login?safe_repair=1। Safe repair session শুধু recovery routes-এ plugin/theme bypass করে; সাধারণ content access বা Owner policy bypass করে না। Healthy site-এ dashboard-এ ফিরতে Open dashboard ব্যবহার করুন।
- Root ও subfolder installation-এ /admin/login, /admin/two-step, /admin/connection-status এবং /admin/updates খোলা থাকবে। Normal dashboard বন্ধ থাকলে sign-in-এর পর Site recovery-তে যাবে; login redirect content page-এ পাঠিয়ে আবার আটকে রাখবে না। Maintenance mode-এও এই authentication/repair endpoints চলে।
- Recovery mode-এ active plugin/theme functions, scheduled publication ও custom content redirect না চালিয়ে normal authenticated dispatch ব্যবহার হয়। Password, two-step, banned account, session revision, admin role ও CSRF checks বহাল থাকে। Public site/content editing-এর restriction উঠে যায় না।
- Site recovery → Upload official ZIP / repair-এ complete signed ZIP দিন। এই lightweight screen খুলতে central বা GitHub-এ নতুন check লাগে না। Package upload/apply-এর existing validator publisher signature ও hashes আবার পরীক্ষা করে, automatic backup বানায়, same-version repair করে এবং data/identity/settings রাখে। Update running থাকলে parallel data restore বন্ধ।
- Files ঠিক হওয়ার পর saved connection ক্ষতিগ্রস্ত থাকলে current admin password দিয়ে Reverify official connection ব্যবহার করুন। Official fixed authority certificate ও exact site proof/local private installation key আবার যাচাই হয়। Identity, paid/license records ও Owner suspension/ban reset হয় না। Verification ব্যর্থ হলে আগের connection state ফেরত থাকে।
- Signed response-এ Owner action ও integrity failure আলাদা থাকে। Official files restored হলে, central outage চললেও সর্বশেষ signed Owner Active/Warning সিদ্ধান্ত মানা যায়; Owner Suspended/Banned হলে repair করেও site চালু হবে না।
- Normal repair path-এর bootstrap, authentication/database ও updater components execute করতে পারা প্রয়োজন। সেগুলো deleted, syntax-broken বা corrupted হলে web-only repair-এর নিশ্চয়তা নেই; matching official files বা trusted full backup hosting recovery দিয়ে restore করতে হবে। Malicious code ইতিমধ্যে execute হয়ে থাকলে শুধু file repair-কে complete incident cleanup বলা হচ্ছে না।

Updater requests request a bounded 300-second PHP budget and preserve repair access after catchable timeout/fatal interruption. A process hard-kill can prevent cleanup. On the co-located Owner site, updating Server first provides the budget for an older CMS apply/upload request. Standalone old CMS installations do not acquire new PHP code before the first update executes: if their host enforces too little execution time for backup/update, a one-time hosting time-limit adjustment may be needed. No unsafe downgrade or signature/authentication bypass is recommended.


Configuration compatibility correction (CMS 1.2.1): per-site config/*.php templates are retained by the updater and excluded from immutable runtime hashes. Publisher-signed core, central registration/policy/authentication and update verification remain enforced. Post-update health now checks the installed signed runtime before success.
